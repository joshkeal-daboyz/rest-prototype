## What the ticket asked for, as I understood it
A lit building's windows glow through a per-instance `windowLevel` attribute on the shared building instancers, read by one `onBeforeCompile` hook on the colourway materials. L1's per-building material clones and F1a's `exclude` path go, so lighting buildings adds no draw call and no program.

## Does the branch do it?
- **1, the level attribute.** The code is there. `plan3d.ts` `buildingBoxes` gives each instancer its own `BufferGeometry`, which shares the root's attributes and index and adds a zeroed `InstancedBufferAttribute` named `WINDOW_LEVEL`. Each instancer's material is a `windowLit` twin, one per painted source material, made at build. `windows.ts` `windowLit` clones the material once and sets emissive white, `emissiveMap = windowMask()` and `emissiveIntensity = WINDOW_LIT`. Its `onBeforeCompile` multiplies `totalEmissiveRadiance` by the varying instance level, with one `customProgramCacheKey`, so emissive = mask x level x `WINDOW_LIT` as asked. `setBuildingGlow` writes only that building's slots with `windowIntensity / WINDOW_LIT`, so the flare is in. It marks an attribute for upload only when a slot changed. The test is `windows.test.ts`, "lighting a building writes only its instances' window level...". It checks that the other building's slots and its attribute version are untouched and that the material is the same object, and the flare value is right.
  The gap: the test runs on InstancedMeshes it builds by hand, not on F1a's fixture as the criterion says. Nothing checks that `plan3dGroups` puts the attribute (at 0) and the twin material on its building instancers. `setBuildingGlow` skips an instancer with no attribute (`if (!attr ...) continue`). So if the `geo.setAttribute(WINDOW_LEVEL, ...)` line in `plan3d.ts` were deleted, every test would still pass and no window would light. `grep WINDOW_LEVEL src/render3d/*.test.ts` finds only the windows test. That half of the criterion is not covered (must-fix 1).
- **2, L1's clones go.** `litBuilding`, `LitBuilding`, `placedClone`, `NO_EXCLUDE`, the `exclude` argument and `BuildingsDraw.groups` are all removed. No reference is left in `src/render3d/`, and CI's typecheck passed. F1a's "keeps an excluded building as clones..." case is removed. `drawLive` calls `setBuildingGlow(city.buildings, b.id, bg)` for each of `lampsOf`'s buildings. `litGlass` is unchanged. Met.
- **3, no program in play.** This one is checked in the browser. The main session's readings on the district view are 1,855 draw calls and 11 programs both before power and after the Relight, and 1,714 building-piece calls both times. That meets "no new program" and "calls after <= calls before + 1". The twins are drawn from the first frame, so their program compiles before play. There is no explicit `gl.compile`, but the readings show none is needed. Met on the main session's readings.
- **4, the bar.** The builder reports M2's rows; I did not run the browser. I can't tell from the code, so it goes to the main session and the builder's report.
- **5.** Josh's play. Not judged here.
- **Count.** 2 `it(` lines added against `origin/main`: the rewritten windows case, and the plan3d "with empty roots instances no piece..." case, renamed and rewritten because `groups` went. The ticket's net count is 1. Both are well under 15, and the second is forced by criterion 2. Both test files pass locally (84 tests, 55.7 s for the two files).

## Rule conflicts and risks
- No hard-rule break. Every change is in `src/render3d/`, with no new dependency and no change to `src/grid/` or `src/night/`. `windows.ts` imports only a type from `plan3d.ts`, so the new value import from `plan3d.ts` into `windows.ts` makes no runtime cycle.
- The diff goes a little past "`plan3d.ts`: the attribute and the material hook only". It removes `placedClone`, `exclude` and `groups`, rewords "cloned" to "instanced" in the comments, and rewrites the plan-assemble report string. All of that follows from criterion 2 except the comment wording, which is harmless.
- **Shared GPU buffers on dispose (may occur, not checked in a browser).** `BuildingsDraw.dispose` now calls `m.geometry.dispose()` on each instancer's geometry. In Three (`three.module.js`, `destroyGeometry`), that deletes the GL buffers of every attribute and the index the geometry holds. Here those are the cached root's position, normal, uv and index, shared through `sharedTileModels`. In cityview the old city is disposed before the next one first renders, so the next one's new geometries upload the buffers again, and the main session's readings show nothing broken. A mesh drawn at the same time from the same root geometry would still point at a deleted buffer. That could be another renderer, or a future layer drawing the same building keys.
- Every building now uses the twin, not only the lit ones. At level 0 the emissive is zero, so an unlit building loses any emissive colour its source material had. If the pack's building materials have emissive black (the usual case), the look is unchanged. I did not check the materials.

## Must fix

Run `plan3dGroups` on the three-building fixture. Check that every building instancer's geometry has a `windowLevel` attribute of length `count`, all 0. Then `setBuildingGlow` one building, and check that its instances' slots carry the level, the other buildings' slots stay 0, and each instancer's material is the same object before and after. Expected effect: losing the attribute or the twin in `buildingBoxes` makes a test fail, where today nothing does.

## Could improve
1. In `BuildingsDraw.dispose`, don't call `geometry.dispose()` on geometries whose attributes belong to the shared roots. At most, drop the instancer's own `windowLevel` attribute. That way a rebuild can never delete GPU buffers another live mesh is drawing from (see Risks).
2. `windowLit` copies the source's `emissive` only in the sense that it overwrites it with white. A note, or a check that the building atlas materials have emissive black, would make clear that unlit buildings look exactly as before F1b.
3. The "cloned" to "instanced" comment rewording in `plan3d.ts` is outside the ticket's narrow plan3d scope. It is harmless, but it could be left out to keep the diff to what the criteria need.
