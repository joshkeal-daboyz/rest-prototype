## What the ticket asked for, as I understood it
A `tools/` fit tool (`npm run fit`) that embeds a schematic puzzle on 6 x 6 seed 1 in a district of 1 to 4 blocks and writes a draft `puzzles/city/<id>.city.json`, or says why it can't. Also: `npm run check` covering city puzzles, with the mid-row clearance check (B1b K2 check 11), and section S's `raiseForScenery`, which writes the raised capacities and ratings into every draft and, through `--raise`, into P0 and hand reworks.

## Does the branch do it?
I reviewed the builder's commit b77e14b against the goal branch `ticket/081-puzzles-on-the-city`. It touches only `package.json` (the `fit` script), `tools/check.ts`, `tools/check.test.ts`, `tools/fit.ts`, `tools/fitrun.ts` and `tools/fit.test.ts`, all of which the ticket lists. The test cases come to 12, as the ticket's count says: 10 in `fit.test.ts`, 2 in `check.test.ts`. I ran both files with 2 workers and all 33 pass. `fit.test.ts` took 3.9 s, almost all of it the shared city build in `beforeAll`, which the ticket allows ("through the module cache"). `check.test.ts` took 10.3 s, of which the two new cases are 3.4 s and 4.0 s.

It also checks that line ends sit on `~a`/`~b`, faults, parts and targets, and that the only added ids are in `hidden`. The second case checks that the raised draft differs from the unraised one only in capacity and ratings.
4. **Deterministic.** Met. The "criterion 4" case makes two identical calls and compares the JSON.
5. **Budget.** Met. With `budget: 1` the result is `kind: "gave-up"` and the message is "gave up after N steps (FIT_BUDGET 1)".
6. **`npm run check` covers city puzzles.** Met, by the 2 cases in `check.test.ts`. `checkCityFile` runs the shape check, then `cityCheckProblems` (CK12 to CK14, CK17d and the mid-row check), then the note's block on the conversion. 7. **One sweep.** Met. `fit.test.ts` "the sweep" checks every `puzzles/city/*.city.json` through `checkFile` on the shared plan. Today that is 1 puzzle, in 11 ms.
8. **The fit report** has no test. It is the builder's reply, which I did not read.

The test finds one blocked and one clear mid-row place on the real seed-1 plan: the blocked one gives `CK17a`, the clear one gives nothing. 10. **The raised numbers.** `raiseForScenery` is right. The `npm run fit -- --raise` path for hand reworks is not (must fix 1). The test turns P0's `j_sh` into a fuse box rated 4, replays the solution with everything unlimited, and splits the lit scenery lamps into those on `l_feed`/`l_n`/`sw` (before the fuse) and the rest. It expects the capacity to be 3 plus all of them and the rating to be 4 plus the rest. I checked that split against P0's file. At the end of `["sw", "repair:l_e2"]` the switch feeds `l_n` to `j_sh`; `l_s` and `l_homes` are dead, and everything lit past `l_n` (`j_sh`'s own building, `l_shrine`, `l_e2`, `l_inf`, and `l_x` up to its cut) is under `j_sh`. Without `base`, the call would raise the already raised 25 again, so a base is the only reading under which the criterion can hold. I accept it.

## Rule conflicts and risks
- **`src/grid/` and `src/night/` are not touched.** The fit and check code reads them through `tools/checkrun.ts`, as before. No new dependency. No GDD Decided rule is changed: scenery lamps stay leaves, and a building past a cut stays dark because S1's conversion handles that.
- **The phantom target lamp** (`unlimited()` in `tools/fit.ts`). `src/grid/` refuses moves once the job is complete ("the job is already complete" in `checkrun.ts`'s `play`). With unlimited numbers the job can complete before the solution's last move, which would then fail or be skipped. The extra `~never` target goes only on the throwaway replay copies, has no line, carries no load and is never written to a file. It is a sound way to take every move. I see no rule it bends.
- **09, 12 and 14 found by searching past embeddings.** `fitPuzzle`'s `accept` (`playsLikeSchematic`) skips any embedding whose raised start (lit file lamps, readable faults, blown fuses, brownout) differs from the schematic's, or that does not win by the solution. So the fit does P2a's fix (a), the re-lay, by itself for every pilot. That fits fix (a)'s wording ("another district or route than the fit's first"). The stop rule asks whether "a pilot it fits" plays the same, and what the fit returns does. But 14 was not in the pre-check's list, and it plays the same only because the search passed over its first embeddings. Josh and P2a's designer should hear that from the main session; it should not vanish into the tool. `accept` checks only the start and the win. The full stop-rule measure (fewest clicks, winning configs, dead first moves, blows on the shortest win) is `fitrun.ts`'s `report`, which exits 3 on a difference, so a draft that passes `accept` but differs on the analyzer's numbers is still flagged.
- **`tools/fit.ts` imports `src/city/facades/roofs` and `src/city/facades/place`.** It only reads them, for roof footprints and the column frame. `tools/` already imports `src/city/circuit/`, and the folder-purity rule binds only `src/grid/` and `src/night/`. No other folder's files are edited. Not a conflict.

## Must fix
1. **`npm run fit -- --raise` overwrites a hand rework's own capacities and ratings with the schematic's** (`tools/fitrun.ts`, `raiseFile`). Every rework keeps `from` set (the ticket: "a new file `puzzles/city/NN-slug.city.json` with `from` set"). So `raiseFile` always finds the schematic and passes it as `base`, and each raised number becomes the schematic's number plus the scenery load. A rework may change capacities and ratings (answer 4), and criterion 10 names "hand reworks" as what `--raise` is for. Two cases where it goes wrong: 09's fix (b), where the designer sets `fb_A`'s rating and then raises the file, and 15's rework. Both would get the schematic's numbers back without warning. There is a second effect: a feed in the rework that the schematic lacks has `was === undefined`, so its extra load goes into the top-level `capacity`, and a new fuse box is not raised at all. I found this by reading `raiseFile` and `raiseForScenery`. I did not run it: no rework file exists yet. **Expected:** raise from the schematic's numbers only when the file is the schematic raised, not reworked (its node, line and fault ids, types, loads, parts and targets are the schematic's). Otherwise raise from the file's own numbers, and print which base was used. A rework run twice through `--raise` would then double-raise, so either refuse or warn on a second run, or have the rework's note record its unraised numbers. No new test is needed for this: it is CLI glue, and criteria 10 and 11 already hold `raiseForScenery`.

## Could improve
1. `fitrun.ts`: print how many embeddings the fit passed over because they did not play the same raised (today `districtsTried` counts districts, not embeddings). The designer would then see, as for 14, that the fit's first lay failed and a re-lay was taken.
2. `tools/check.test.ts`, the CLI case: pass the timeout as a number (`120000`), not `{ timeout: 120000 }`. Vitest warns that the object form will throw in Vitest 4. That case also takes 4 s to spawn `tsx` and build the city in a fresh process. Spawning `check.ts` on a cheap schematic file would cover the CLI wiring, and the first case already covers the city path.
3. `fit.test.ts` criterion 2: build the switch-heavy schematic from the district's actual 3-attachment count plus 1, and assert the exact "district has N". Today `\d+` would pass with a wrong count.
4. `fit.ts` `shortfall`: `terminals` is computed and then `void`-ed. Drop it.
5. The sweep's `console.log` of its time: drop it once the time is reported. It is fine as a line inside a test that asserts.
6. A small amount of extra scope: `--unraised`, `--max-blocks` and `--out` in `fitrun.ts`. They are harmless and useful to the designer, so keep them if the main session agrees.
