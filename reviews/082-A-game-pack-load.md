## What the ticket asked for, as I understood it
One pure list of what the page asks the loader for (`pageloads.ts`), one sorted, unique list of every model the game loads (`gameModelKeys()`, `gameColourways()`) for B to cut, and a loader that uses `out/game/manifest.json` only when it is readable, carries `game` and covers every key the call asks for. Otherwise it loads the full packs as today and says why in one line. Plus a dev-only `?packs=full` and a dev-only load line. The measurements (6) and the side-by-side views (7) need B's game pack.

## Does the branch do it?
Reviewed commit 5f1f937 (the only commit on `ticket/082a-game-pack-load` that is not on the 081 branch) against origin/main.

1. **The load lists in one place: met.** `src/render3d/pageloads.ts` holds `pageLoadLists(extra)`, `TECH_KEYS`, `HOLDOUT_KEYS`, `RUIN_KEYS`, the `STEPS_KEY` choice and `allStackPieceKeys()`. It imports neither `models3d.ts` nor `plan3d.ts`, and none of its own imports (`dressing`, `furniture`, `models`, `sills`, `stacks`, the three city kits) reach either one, so there is no cycle. `loadPageModels` now spreads `...pageLoadLists(extra)`. That gives the same stack, dress, step and `extra` fields, in the same order, as the old inline call, so each page asks for what it asked for before. `allStackKeys()` stays exported from `models3d.ts` and returns `allStackPieceKeys()`, which is the same expression it had before.
2. **`gameModelKeys()` and `gameColourways()`: met.** In `src/render3d/gamemodels.ts`, `gameModelKeys()` is the sorted set of `listedKeys` for both page calls (`schematicLoadLists()`, and `cityLoadLists()` with `planKeys()` and `[STOP_SIGN_COLOURWAY]`, matching `sharedTileModels`), `tileKeys()`, and the circuit keys named on their own (`GROUND_POLE_MIX`, `POWER_LINE`, the non-null `COMPONENT_MODELS` keys, `STREET_LIGHT_KEY`). `gameColourways()` is the pool without `base`, plus the stop sign's id, sorted. The test is `gamemodels.test.ts`, 1 case, exactly as the ticket asks: sorted and unique, every key of both calls included (it also guards against a vacuous pass with `> 100`), and every non-null component key included.
3. **The loader prefers the game pack: met.** `readGamePack` in `models3d.ts` fetches `${dir}game/manifest.json`. It returns the manifest only if `isManifest` holds, `game` is set and `listedKeys(asked)` is fully covered by the manifest's `pack:name` entries. `asked` uses the same defaults `loadModels` uses (`table ?? MODEL_TABLE`, the others `?? []`). In that case `dir` becomes `…/out/game/` and the full manifest is never fetched. In every other case it returns null and the full `manifest.json` path runs unchanged. The two lines match the ticket's wording. **A stale or partial manifest is never used in part:** there is one decision per call, made before any GLB is planned. A single missing key sends the whole call to the full packs, and no code path mixes the two dirs. Tests: `gamepack.test.ts`, 2 cases with fake `fetchJson`/`loadGlb`. (a) A covering game manifest: the only GLB URL is `/out/game/p.glb`, `/out/manifest.json` is never fetched, the pole comes from it and no line is printed. (b) A game manifest lacking `p:Lamp`: the GLB is `/out/p.glb`, and exactly one line names `p:Lamp` and `npm run assets:game`. Both fail if the coverage check is removed or loosened. `models.test.ts` gains `gamePack: false` in its shared `deps()` helper, so the existing line-counting cases run as before. That is a fixture change, not a rewritten case.
4. **`?packs=full` is dev-only: met.** `full = import.meta.env.DEV && typeof location !== "undefined" && …get("packs") === "full"`. A production build always passes `gamePack: true`, and the flag cannot be read there.
5. **The load line is dev-only: met in code, not verifiable here (browser).** `loadLine` runs only under `import.meta.env.DEV`. It sums `encodedBodySize || transferSize` over `.glb` resource entries, names the manifest `game`/`full`/`none` from the GLB URLs, and times from the first `fetchJson`. The resource-timing buffer is raised to 5000, also dev-only, with the reason in a comment.
6. **Measured: with B.** The `## Measured` section of the ticket on this branch is still the placeholder. The "after" run and the medians need B's game pack. Not a must-fix.
7. **Looks the same: with B** (browser, Josh views it).
8. **The gallery is unchanged: met.** `assetviewer.ts` is not in the diff.

## Rule conflicts and risks
- No hard-rule break found. `src/grid/` and `src/night/` are untouched. There is no new dependency. The edits stay in `src/render3d/`, as listed, apart from the one-line `models.test.ts` helper edit: the ticket names `models3d.test.ts`, but the loader's existing cases live in `models.test.ts`, so this is the file it meant.
- The pull request into `main` (#48) also carries the 081 branch's commits not yet on main: the 082 cut (`src/core/assets.ts`, the ticket files), three 081 reviews, and a `.claude/launch.json` entry for an `081-k3` dev server. None of these is A's work. The cut was approved with the ticket, but the main session should know the launch.json entry rides along.
- Partial at a level the criterion does not cover: if a game GLB fails to load, or a root is missing from it while its manifest covers every key, that pack's models fall back to placeholders exactly as a full GLB's do today. There is no retry from the full pack. This is the existing behaviour, and B's atomic write (B criterion 3) makes it unlikely.
- Colourways are not part of the coverage check. A game manifest whose `colourways` lack a pool id would still be used, and that id would be dropped with `loadColourways`' existing line. This may occur if `COLOURWAY_POOL` grows after a cut; I did not check it. Within the criterion, which names keys only.
- `gamemodels.ts` imports `circuitdraw.ts`, which imports `models3d.ts` and `three`, so B's `tools/` script will load `three` and `GLTFLoader` in Node to read `STREET_LIGHT_KEY`. It works under Vitest. B should know about it.

## Could improve
1. `src/render3d/gamemodels.ts`: once K3's circuit keys are confirmed in `planKeys()`, take `STREET_LIGHT_KEY` from a lighter module (or a literal pinned by a test, as K3 did for `FEED_POLE_KEY`). B's Node import would then not pull in `models3d.ts` and `three`.
2. `src/render3d/models3d.ts`, `readGamePack`: also require that the game manifest's colourways include every id the call would fetch (the pool without base, plus `signColourways`). A game pack cut before a pool change would then also be refused whole, rather than painting fewer colourways.
3. The no-game-pack line is not exercised by any test, because the existing cases opt out with `gamePack: false`. If a test slot is ever free, one assertion of that line in case (b)'s fixture style would cover it. It is not needed for this pull request.
